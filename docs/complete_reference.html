Architecture at a Glance

Two kinds of data enter this system — trades (generated automatically) and daily FX rates (a file someone uploads once a day) — and flow left to right through a medallion architecture (Bronze → Silver → Gold). Two orchestration paths are fully built; only one runs at a time. Terraform and GitHub Actions build and check everything underneath.

AWS side (terraform/aws.tf): an S3 bucket (versioned, encrypted, public access blocked), a read-only IAM policy scoped to the fx_rates/ prefix, and the IAM role Snowflake assumes. The role's trust policy needs values Snowflake only generates after the storage integration exists, and the integration needs the role's ARN as input — resolved in one terraform apply by predicting the role's ARN from account_id + role name (deterministic) rather than the usual two-pass setup.

Both roles are granted to the account user PRAVEENMS91 and given USAGE on the warehouse/database. The transformer role additionally gets CREATE TABLE / CREATE VIEW on SILVER and GOLD, and SELECT on all present-and-future tables/streams in BRONZE. The loader role is scoped narrowly to INSERT/SELECT on TRADES_RAW and READ/WRITE on TRADES_STAGE only. A Task's own ERROR_INTEGRATION property only accepts cloud-messaging integrations (SNS/Pub-Sub/Event Grid), not EMAIL, which is why failure alerting goes through a separate ALERT object instead.

Orchestration is split deliberately across two systems rather than having one do everything: Snowflake Tasks handle ingestion (generation and COPY INTO, on independent minute-level schedules, matching the case study's "Ingestion: Snowflake Native" guidance), and dbt Cloud handles transformation (run/test hourly, snapshot monthly) — this describes the cloud-native path as originally designed and fully provisioned. dbt Cloud could technically run ingestion too via dbt run-operation, but that would collapse the two tasks' independent cadences into dbt Cloud's hourly schedule and use a transformation tool to run non-dbt SQL — not done, on purpose. As of this reference, all three ingestion Tasks and the failure alert are suspended and dbt Cloud's own job schedules are switched off, with Airflow running as the sole active trigger instead (see Sections 1, 8, and 11–12) — a deliberate, reversible decision to avoid two schedulers racing the same live objects, not a change to how the Snowflake-native path itself is built.

Why fx_rates exists: Snowflake's COPY INTO treats an edited file re-uploaded under the same name as new rather than overwriting, so a corrected rate file can legitimately create a second row for the same (as_of_date, currency) in FX_RATES_RAW. fx_rates resolves it with the same merge-on-latest pattern as fct_valid_trades — verified live by deliberately re-uploading an edited rate file and confirming BRONZE kept both rows (for audit) while SILVER showed only the latest.

4

The GOLD Star Schema, and Why Some Tables Are Permanent

fct_valid_trades and fct_rejected_trades carry a surrogate-key foreign column for every dim_* table (trader_key, book_key, counterparty_key, product_key, currency_key, trade_date_key, maturity_date_key). gold.yml tests every one of those FKs with a relationships test against its dimension's key — 68 tests total, up from 19 before this redesign. The natural-key text columns (trader, book, counterparty, product_type, currency) are kept on the facts too, alongside the *_key columns — a deliberate denormalization for a handful of small, fixed-vocabulary codes, so a simple query doesn't have to join every dimension just to read them.

dbt-snowflake defaults every table/incremental model to TRANSIENT (no Fail-safe storage) unless told otherwise. Most models here leave that default in place — explicit now, via transient=true — because they're a pure function of BRONZE (permanent) plus the current dbt SQL: if lost, dbt run regenerates them exactly, so Fail-safe's extra 7-day recovery window would be cost with no benefit. fct_rejected_trades and valid_trades_snapshot are the deliberate exception (transient=false): both are point-in-time compliance records of what business logic decided when a message or a snapshot ran — if the rules ever change later, replaying BRONZE would apply new rules to old messages and silently rewrite audit history, so these two earn the extra protection a real audit record deserves.

fct_valid_trades, fct_rejected_trades, and BRONZE.TRADES_RAW carry explicit clustering keys (cluster_by) on maturity_date / to_date(loaded_at) respectively — illustrative at this project's row count, but aimed at the exact query pattern rpt_trade_report's dashboard filter uses (a maturity-date range). observability/observability_toolkit.sql checks clustering health via SYSTEM$CLUSTERING_INFORMATION() and demonstrates a TEMPORARY table for session-scoped ad-hoc debugging that needs no manual cleanup.

RBAC & Data Masking

Two read-only consumer roles sit alongside the two service roles (LOADER, TRANSFORMER): TRADE_ANALYTICS_COMPLIANCE sees everything in GOLD unmasked, including fct_rejected_trades (the audit log) and the raw fact/dimension tables. TRADE_ANALYTICS_ANALYST sees only fct_trade_status and rpt_trade_report — not the underlying tables — with COUNTERPARTY pseudonymized and NOTIONAL/NOTIONAL_USD rounded to the nearest $1M.

The roles themselves are Terraform-managed (terraform/rbac.tf), but who can select what is managed by dbt: a +grants config in dbt_project.yml grants every GOLD object to COMPLIANCE by default, and the two masked models override that individually to add ANALYST — deliberately not granted at the folder level, so it can't reach fct_valid_trades directly and read NOTIONAL/COUNTERPARTY unmasked. dbt re-applies these grants on every run via its native grants model config.

Masking is two Snowflake masking policies (macros/create_masking_policies.sql, created idempotently via an on-run-start hook), each a CASE WHEN CURRENT_ROLE() IN (...) expression, attached via a post_hook on both consumer-facing views. Verified live by connecting as each role: rpt_trade_report returns masked values for ANALYST and real ones for COMPLIANCE, and ANALYST is denied on fct_valid_trades directly — once secondary roles are turned off (Snowflake sessions default to secondary_roles=ALL, which combines every role granted to a user; this trial account's single user holds every role, so isolating ANALYST's own privileges for testing needs USE SECONDARY ROLES NONE first).

The Big Picture, Plain-English

Two kinds of data enter this system: trades (generated automatically, every couple of minutes) and daily FX rates (a file someone uploads once a day). Both flow left to right through three "cleanliness" stages — Bronze, Silver, Gold — a pattern called a medallion architecture. Each stage only trusts data that has passed the checks of the stage before it, so by the time data reaches Gold, it's safe for a report, a dashboard, or a finance team to rely on.

1
S
Sources
Trade Generator — Snowpark, ~every 2 min
S3 Upload — FX rates, once daily
2

BRONZE Raw landing. Nothing checked yet — every row kept, duplicates included, for audit.
3

SILVER Cleaned, deduplicated, and every business rule decided — once.
4

5

Why it's built this way
1Runs natively inside Snowflake. The generator is Snowpark Python, not an external script — no server to babysit, no separate compute bill.
2Deliberately decoupled schedules. Generation and ingestion run on independent cadences, so Bronze reflects a real, imperfectly-synced upstream feed — not a toy lockstep pipeline.
3Rules decided once, duplicates defended twice. Accept/reject logic lives in exactly one model, and duplicates are guarded against both at the loader and again at the Bronze→Silver boundary — nothing to drift out of sync, nothing slips through either check.
4Status computed live, never stored. Active/Expired is worked out fresh on every read — always correct, no job has to "remember" to update it.
5RBAC split by design. Terraform owns who the roles are; dbt owns what each role can see — so the two never fight over the same grant.
Bronze = unfiltered, as-received Silver = validated, business rules decided Gold = final, ready to use
OrchestrationTwo paths are built; only one runs at a time. Airflow (local, against the same live account) is currently the sole trigger, hourly. Snowflake Tasks + dbt Cloud are fully provisioned as the alternative, currently switched off.
MonitoringAirflow emails on any DAG failure (its own SMTP config) — the currently-active path. The Snowflake-native Alert + dbt Cloud's own failure emails exist too, just idle alongside the Tasks they'd watch.
Built byEvery piece above — warehouses, schemas, tables, tasks, the S3 connection — is defined as code in Terraform, rebuildable from scratch on demand.

Component-by-Component Walkthrough

Read top to bottom — this follows the same left-to-right order as the diagram above.

🏭

Trade Generator (Snowpark Procedure)

entry point

A small Python program that lives inside Snowflake (not on anyone's laptop). Every couple of minutes it invents a batch of realistic-looking trades — new trades, amendments to old ones, the occasional duplicate or already-expired trade thrown in on purpose — and writes them as a file directly into Snowflake's own storage.

Why inside Snowflake, not an external script? No separate server to keep running, no laptop that has to stay on, no extra AWS bill for compute — the same warehouse that does everything else runs this too.
Think of it as a practice dummy at a shooting range: it fires realistic shots (trades) on a schedule so the rest of the system has something real to process, without needing an actual trading desk hooked up.
📤

S3 Upload (Daily FX Rates)

entry point

A second, independent data source: once a day, someone drops a CSV file of currency exchange rates (e.g. "1 EUR = 1.081 USD") into an Amazon S3 bucket. Snowflake has been given a narrow, read-only key to look into that one folder — nothing more.

Why S3 instead of another Snowflake stage? This mirrors how data really arrives in most companies — from a different system entirely, owned by a different team, sitting in cloud storage that isn't Snowflake's. It's a genuinely separate, realistic integration rather than a second copy of the same trick.
Like a supplier dropping off a box at your loading dock once a day — you don't control when exactly they show up, so you check the dock on a schedule rather than waiting by the door.
🥉

BRONZE — Raw Landing

bronze

Two scheduled jobs (Snowflake "Tasks") move data from where it lands into permanent tables: one checks the internal storage for new trade files every 2 minutes and loads them; another checks the S3 folder once a day for new rate files. Nothing is validated here — Bronze's only job is "get it in, keep a permanent copy, don't lose anything."

Why not validate immediately? Keeping raw data as-received, untouched, means you can always re-run everything downstream from scratch if a business rule turns out to be wrong later — you haven't thrown anything away.
🌊

The Stream (Change Tracking)

bronze

A Snowflake "Stream" sits on the raw trades table and remembers exactly which rows are new since the last time something looked. The next stage reads from the stream, not the raw table directly, so it only ever processes new arrivals — never the same trade twice, never a full re-scan of history.

Like a "new mail" tray instead of the entire filing cabinet — you only look at what's landed since you last checked.
🪟

BRONZE's dbt Views

bronze

Two very simple dbt "models" sit in Bronze too — base_trades_raw and base_fx_rates_raw — each just a plain "show me everything in this raw table" view. They don't clean or filter anything; they exist so Bronze shows up as a real, clickable part of the data lineage diagram instead of an empty gap before Silver.

Like a reception desk sign that just says "everything received today is in that pile" — it doesn't sort the mail, it just makes the pile visible and pointed-at.
🥈

SILVER — Cleaning & Business Rules

silver

This is where the real decision-making happens, in two steps:

Step 1 — Flatten: raw trade messages arrive as one blob of JSON; this step breaks them out into normal columns (trade ID, version, maturity date, notional amount, currency, and so on).

Step 2 — Decide: every trade message is checked against the business rules and gets exactly one verdict: accepted or rejected, with a reason recorded either way:

Older version arrivesRejected — a newer version of this trade is already on file, so this one is stale.
Same version arrives againAccepted — treated as a correction/replay, replaces what's on file.
Maturity date already passedRejected — this trade would be born already expired, which isn't valid.
Two versions in one batchThe newer one is accepted; the older one is logged as rejected rather than silently thrown away.
Why one single place for all these decisions? If "accept or reject" logic were scattered across several files, they could quietly drift out of sync with each other over time. Having exactly one decision point means there is exactly one place to look, trust, and test.
🧹

FX Rates, Deduplicated

silver

Bronze never deletes or overwrites — if someone edits an FX-rate file and re-uploads it under the same name, the system treats it as a brand-new file and keeps both the old and corrected values sitting in Bronze. A Silver step resolves that: it always keeps exactly one row per day per currency — whichever value was loaded most recently — while Bronze quietly holds onto the full history underneath, in case anyone ever needs to see what changed.

Like a whiteboard that always shows today's number, while a logbook underneath records every correction anyone ever made to it.
🥇

GOLD — Business-Ready Tables

gold

Three core tables, each with one clear job:

fct_valid_tradesThe current, accepted state of every trade — one row per trade, always the latest version.
fct_rejected_tradesA permanent audit log of every trade that was turned away and why — needed for compliance, never edited or deleted.
fct_trade_statusA friendlier view for reporting: adds "Active" or "Expired" (worked out fresh every time it's queried, from today's date vs. the maturity date — not a stored flag that could go stale) and converts each trade's amount into US dollars.
Why compute "Expired" on the fly instead of storing it? A trade's expiry status changes automatically as time passes — there's no button anyone presses. Computing it at read-time means it's always correct, with no separate job needed to "remember" to update it.
🗂️

The Dimension Tables (Star Schema)

gold

Six small lookup tables sit alongside the two tables above: one each for trader, book, counterparty, product type, currency, and calendar date. Every trade in fct_valid_trades/fct_rejected_trades points at a row in each of these instead of just repeating the plain text — "trader_d" is really a link to a row in the trader lookup table, not just a string typed in six different places.

Why bother, if the plain text was already there? This is a standard reporting-database pattern called a star schema. It lets tools double-check that every trade actually points at a real trader/book/counterparty (a "does this link actually go anywhere" test, which this project now runs automatically), and it's the shape most BI/reporting tools expect. The plain-text version is deliberately kept too, side by side, so a simple question doesn't require following the links.
Like a form with a dropdown list instead of a free-text box: picking "Barclays" from a dropdown guarantees it's a real, known counterparty, rather than trusting that everyone typed the name identically every time.
📋

The Reporting Layer

gold

One more table, rpt_trade_report, flattens everything above into a single, wide table built specifically for reporting: every trade attribute already spelled out as plain text, plus handy extras like "which quarter did this trade mature in" and "how many days until maturity." Nobody using this table has to know the star-schema link structure underneath it at all.

Why a separate table just for this? The star schema (previous section) is great for a BI tool that already knows how to follow links, but it's awkward for a quick filter-and-look dashboard. This table exists purely so that job is a single flat query, with no links to follow.
💱

The Currency-Conversion Macro

gold

A small reusable piece of code that turns "this trade is 5 million EUR" into "this trade is about 5.4 million USD," using a table of exchange rates. Instead of writing that conversion logic by hand everywhere it's needed, it's written once and reused — change a rate in one place, and every report using it updates automatically.

Like a currency converter widget you plug into any spreadsheet, instead of re-typing the conversion formula in every single cell.
🕰️

Monthly History Snapshot (Type 2 SCD)

gold

valid_trades only ever shows "right now" — it doesn't remember what a trade looked like last month. Once a month, a separate job takes a permanent copy of the current state and files it away with a timestamp, building up a history: "as of the end of January, this trade looked like X; as of the end of February, it looked like Y."

Why does this matter? Finance and compliance teams often need to answer "what did our book of trades look like at the end of last month," not just "what does it look like today." Without this, that question is unanswerable once the data has moved on.
Like a photograph taken on the last day of every month, kept in an album — you can always flip back and see exactly how things looked on that date, even though today looks different.
⏱️

Orchestration — Who Presses "Go"

supporting

Nothing in this pipeline runs because a person clicks a button each time. Two entirely different schedulers are built to run it — but only one is actually switched on at any given moment, on purpose.

Airflow — running locally, against the same live cloud Snowflake account — is the one currently doing the work: an hourly job generates trades, loads them, and runs dbt's clean/rules/marts logic and tests, plus a separate once-a-month job for the history snapshot.

Snowflake Tasks + dbt Cloud — a second, independent way of scheduling the exact same work (Tasks for everything before Silver, dbt Cloud for Silver and Gold) — is fully built and ready, just not currently turned on.

Why build two and only run one? Two schedulers independently triggering work against the same live data caused a genuine bug once — a duplicate trade slipped in because two systems tried to load the same file around the same time. Running exactly one at a time removes that risk entirely, while keeping the second path ready to switch back on whenever it's needed.
🔔

Monitoring & Alerting

supporting

Every scheduled job automatically retries itself twice if it fails, and stops trying (rather than failing forever in a loop) after three failed attempts in a row. Whichever scheduler is currently active emails on failure — right now that's Airflow, using its own mail settings; the Snowflake-native "Alert" (checks every 15 minutes) and dbt Cloud's own failure emails are the same safety net for the other path, just idle alongside it. There's also a ready-made library of copy-paste queries for digging into "what happened and why" when something does go wrong.

🧱

Infrastructure as Code (Terraform)

supporting

Every piece of Snowflake and AWS infrastructure in this system — warehouses, schemas, tables, tasks, the S3 bucket, the permissions connecting them — is written down as code rather than clicked together by hand in a web console. Running one command rebuilds the entire environment from nothing.

Why does this matter? If this environment were lost, recreating it by memory/clicking would be slow and error-prone. With it written as code, rebuilding is fast, repeatable, and exactly reproducible — and every change to the infrastructure has a paper trail (it's tracked in version control, just like the code itself).
🔁

CI/CD (Automatic Checks on Every Change)

supporting

Whenever a change is proposed to the code, automated checks run before it's allowed to merge: the data transformation logic is tested, and the infrastructure code is validated. Deploying new infrastructure changes to the live environment is a deliberate, manual trigger — not something that happens automatically just because code changed.

🗄️

Permanent vs. Disposable Tables, and Sorting the Data Ahead of Time

supporting

Snowflake offers a cheaper table option that skips an extra 7-day safety-net backup — fine for anything that can be perfectly regenerated from earlier data, wasteful for anything that can't. Most tables in this pipeline use the cheaper option, since they can always be rebuilt from Bronze. Two are deliberately kept on the full-price option instead: the rejected-trades audit log and the monthly history snapshot — both are a record of "what was decided at the time," which literally cannot be perfectly recreated later if the business rules ever change.

Separately, the biggest tables are told to keep themselves roughly sorted by maturity date as new data arrives, so a report asking "trades maturing in the next 90 days" doesn't have to look through the whole table to find them.

Why does this matter at such a small scale? It doesn't, yet — this project is far too small to actually need either of these. They're set up anyway, correctly and deliberately, so the choice is documented and ready for the day the data is 10,000x bigger, rather than being retrofitted under pressure later.
Like paying for extra insurance only on the one filing cabinet that holds originals you could never reprint, and keeping the archive roughly filed by date so nobody has to search box by box.
📊

Dashboard — Live, Inside Snowflake

supporting

A web page that queries the reporting table directly and shows, at a glance, how many trades are active vs. expired, and why trades have been rejected recently — with filters down the side (trader, book, counterparty, product, currency, status, and a maturity-date range) so a user can narrow the view to exactly the trades they care about. It's optional and separate from the pipeline itself — it's a consumer of Gold data, not a part of building it. It runs as a Streamlit in Snowflake app: the dashboard's code lives and executes inside Snowflake itself, not on anyone's laptop, so it's always reachable by opening Snowsight rather than something someone has to remember to start.

Why does "runs inside Snowflake" matter? A dashboard that only works when a particular laptop has a terminal open isn't really "live" — it's a demo. Running it as a native Snowflake object means it's on the same always-available compute as everything else in this pipeline, with no separate credentials to manage and no separate hosting to keep paying for.
Like the difference between a report someone has to remember to email out versus a live dashboard on the wall of the trading floor — the second one is just always there.
🔒

Who Sees What

supporting

Two extra Snowflake roles sit on top of the pipeline, read-only: one for compliance staff, who see every trade and the full rejected-trade audit log with real dollar amounts and real counterparty names; and one for general analysts, who see the same reporting screen but with deal sizes rounded to the nearest $1M and counterparty names replaced with a consistent code — enough to spot patterns and totals without seeing exactly who traded exactly how much. The analyst role also can't reach the underlying raw tables at all, only the reporting screen itself, so there's no side door around the masking.

Why mask instead of just hiding the columns? Hiding a column entirely would stop an analyst from doing basic aggregate work — "which product line is biggest this quarter" needs some notional figure to sum. Rounding to the nearest million answers that without exposing one counterparty's exact negotiated price on one specific deal.
Like a company-wide sales report that shows "~$40M" and "Client 7B80959" instead of the exact contract value and the client's actual name — useful for spotting trends, useless for reverse-engineering someone else's deal.

The Role of Terraform — What It Manages

Terraform is this project's infrastructure-as-code tool: instead of clicking through the Snowflake and AWS consoles to create a warehouse, a table, an S3 bucket, or a permission, every one of those things is described in a text file. Running terraform apply reads those files and makes reality match them — whether that means creating something new, changing something that drifted, or (if a file is deleted) tearing something down.

Two cloud providers, one apply. Terraform doesn't just manage Snowflake objects or just AWS objects — a single terraform apply coordinates both, including a genuinely interlocking piece: the Snowflake storage integration and the AWS IAM role that trusts it depend on each other's generated values (see the story in Section 13).

What Triggers a Terraform Run

There are two very different ways Terraform runs in this project — by hand, and via GitHub Actions — and they answer different questions.

TriggerRuns whatApplies changes?Why
Local: a developer runs terraform plan / apply by hand Whatever command was typed yes, if apply Day-to-day development — building and testing new infrastructure changes before they're even committed.
CI: a Pull Request touching terraform/** fmt -check, init, validate, plan no Catches syntax errors, drift, and shows exactly what a merge would change — before anyone approves it.
CI: a push to main touching terraform/** Same as above (plan only) no A safety net even after merge — confirms the merged code still plans cleanly.
CI: manual dispatch (the "Run workflow" button, or gh workflow run) validate first, then apply — sequenced so they don't run at the same time yes The only path that actually changes live infrastructure from CI — a deliberate, human-triggered action, not an automatic side effect of merging.
NotePath filtering matters. Both PR and push triggers are scoped to paths: ["terraform/**"] — a commit that only touches docs/ or dbt/ won't trigger this workflow at all. That's expected behavior, not a bug: it's exactly why, while fixing this workflow, verifying the fix required manually dispatching it rather than waiting for a matching push.
CautionWhy apply is never automatic on push. Provisioning warehouses, roles, and cloud storage on every merge to main is more blast radius than this project needs. apply is one click away (or one gh workflow run away) once a plan has been reviewed — but it's never a surprise side effect of someone else's unrelated commit. GitHub Actions also runs a second, independent workflow (dbt_ci.yml) that builds/tests the dbt project on every PR and merge — it doesn't route through Terraform at all, see the architecture diagram in Section 1.

Why It's Useful — In Practice, Not Theory

Three moments from actually building this project make the case better than a generic list of Terraform's benefits would.

1

The plan that caught a near-miss before it happened

Midway through renaming the schemas to BRONZE/SILVER/GOLD, a routine terraform plan came back showing all three schemas — the ones holding every trade, every rejected message, all the currently-loaded data — marked must be replaced. A single missing setting (is_transient) had drifted between what was actually in Snowflake and what the config said, and Terraform's default behavior for that particular attribute is destroy-then-recreate.

# snowflake_schema.schemas["BRONZE"] must be replaced
Caught by planBecause plan shows every intended action before anything happens, this was caught and fixed with one line of config — instead of discovering it the hard way, after apply had already dropped three schemas.
2

Local and CI disagreeing about what already existed

Early on, the GitHub Actions apply job failed with errors like "a policy called snowflake-fx-rates-read-policy already exists." The workflow checked out a fresh copy of the repository with no memory of what earlier local apply runs had already built, so it tried to create everything again from scratch and collided with itself.

Fixed with shared stateA shared, remote state backend (S3) instead of a local file. It's the same principle as a shared calendar instead of everyone keeping their own: local runs and CI now check the same source of truth before touching anything, and a locking mechanism stops two runs from writing to it at the same moment (verified live — it correctly blocked a second concurrent run rather than corrupting anything).
3

Solving a chicken-and-egg problem in one step

Snowflake's connection to the S3 bucket needs an AWS IAM role that trusts it — but that role's trust policy needs an ID that Snowflake only generates after the connection exists, and the connection needs the role's address as an input. Neither can go first.

Resolved in one applyThe role's AWS address is predictable ahead of time (account ID + role name), so the Snowflake side could be created first using that predicted address, and the AWS role's trust policy was then filled in with the values Snowflake generated — all figured out automatically from the dependencies written in the config, not manually sequenced by hand.
The common threadIn all three cases, the value wasn't "Terraform makes infrastructure faster to create" — it was that the plan, the shared state, and the dependency graph each independently prevented a real mistake that manual console clicks would not have caught in the same way.
