What Terraform Actually Manages Here

Terraform is this project's infrastructure-as-code tool: instead of clicking through the Snowflake and AWS consoles to create a warehouse, a table, an S3 bucket, or a permission, every one of those things is described in a text file. Running terraform apply reads those files and makes reality match them — whether that means creating something new, changing something that drifted, or (if a file is deleted) tearing something down.

Two cloud providers, one apply. Terraform doesn't just manage Snowflake objects or just AWS objects — a single terraform apply coordinates both, including a genuinely interlocking piece: the Snowflake storage integration and the AWS IAM role that trusts it depend on each other's generated values (see the story in Section 3).

FileWhat it defines
versions.tfWhich Terraform version and which provider versions (Snowflake, AWS, Random) this project needs.
backend.tfWhere the project's state — Terraform's record of what it created — actually lives: an S3 bucket, not a file on one laptop. This is what lets local runs and CI see the same reality.
providers.tfConfigures the Snowflake and AWS connections, including the list of still-in-preview Snowflake resource types this project had to explicitly opt into.
variables.tfEvery configurable knob: warehouse size, schedule intervals, the S3 bucket's base name, the alert email address, and more — with sensible defaults.
main.tfThe core Snowflake estate: warehouse, database, the three medallion schemas (BRONZE/SILVER/GOLD), roles and their grants, the JSON file format, the internal stage, the raw landing table, and the CDC stream. The transformer role's grant on BRONZE includes CREATE VIEW alongside USAGE — added so dbt can materialize the BRONZE passthrough views described below, without granting it CREATE TABLE there too. The raw landing table also carries a cluster_by = ["to_date(loaded_at)"] clustering key — illustrative at this project's row count, matched by the same choice on two dbt-managed GOLD fact tables (cluster_by=['maturity_date'], set in their model config, not Terraform).
orchestration.tfThe scheduling layer: the two trade-pipeline Tasks, the email notification integration, and the Alert that watches Task history and emails on failure.
aws.tfThe AWS side of the FX-rates integration: the S3 bucket (encrypted, public access blocked), the read-only IAM policy, and the IAM role Snowflake assumes to read it.
s3_integration.tfThe Snowflake side of that same integration: the storage integration (the trust relationship itself), the external stage pointing at S3, the CSV file format, the landing table, and the daily ingestion Task.
streamlit.tfThe trade dashboard as a native Snowflake object: a stage to hold the app file(s), the snowflake_streamlit resource itself (already GA in this provider version, not a preview feature), and a USAGE grant so the transformer role can open it.
outputs.tfA handful of values (database name, warehouse name, role names) printed after every apply, for quick confirmation without a separate query.

🧩 Owned by a purpose-built tool

  • BRONZE.GENERATE_TRADE_FILES (the Snowpark procedure) — deployed via a plain SQL script (terraform/sql/) instead of a Terraform resource, so its Python body stays under direct version control in one reviewable file.
  • The state backend bucket itself — bootstrapped once via a small Python script, before the regular apply flow exists to manage it: Terraform's state has to live somewhere before Terraform can track that somewhere.
  • dbt Cloud — jobs, environments, and the Snowflake connection on the dbt Cloud side are managed through dbt Cloud's own API, the tool purpose-built for scheduling and running dbt itself.
  • The BRONZE passthrough views themselves (base_trades_raw, base_fx_rates_raw) and the silver.fx_rates merge-dedup model — these are dbt models, not Terraform resources. Terraform's role stops at granting the transformer role permission to create them (see the CREATE VIEW grant above); dbt owns the SQL.
  • The Streamlit app's file content (Summary.py, common.py, pages/1_Trade_Details.py, environment.yml) — streamlit.tf registers the app object and the stage it lives on; the files themselves are pushed via a one-time PUT, the same pattern used for GENERATE_TRADE_FILES' Python body — application code stays in application files, not embedded in HCL.

🏗️ Owned by Terraform

  • All Snowflake objects: warehouse, database, schemas, roles, grants, stage, file format, tables, stream, tasks, alert, notification integration, storage integration.
  • All AWS objects: S3 bucket + its security settings, IAM policy, IAM role.
  • The connective tissue between them — the exact permission boundary letting Snowflake read (and only read) one S3 prefix.

What Triggers a Terraform Run

There are two very different ways Terraform runs in this project — by hand, and via GitHub Actions — and they answer different questions.

TriggerRuns whatApplies changes?Why
Local: a developer runs terraform plan / apply by hand Whatever command was typed Yes, if apply is run Day-to-day development — building and testing new infrastructure changes before they're even committed.
CI: a Pull Request touching terraform/** fmt -check, init, validate, plan No Catches syntax errors, drift, and shows exactly what a merge would change — before anyone approves it.
CI: a push to main touching terraform/** Same as above (plan only) No A safety net even after merge — confirms the merged code still plans cleanly.
CI: manual dispatch (the "Run workflow" button, or gh workflow run) validate first, then apply — sequenced so they don't run at the same time Yes The only path that actually changes live infrastructure from CI — a deliberate, human-triggered action, not an automatic side effect of merging.
📌 Path filtering matters. Both PR and push triggers are scoped to paths: ["terraform/**"] — a commit that only touches docs/ or dbt/ won't trigger this workflow at all. That's expected behavior, not a bug: it's exactly why, while fixing this workflow, verifying the fix required manually dispatching it rather than waiting for a matching push.
⚠️ Why apply is never automatic on push. Provisioning warehouses, roles, and cloud storage on every merge to main is more blast radius than this project needs. apply is one click away (or one gh workflow run away) once a plan has been reviewed — but it's never a surprise side effect of someone else's unrelated commit.

Why It's Useful — In Practice, Not Theory

Three moments from actually building this project make the case better than a generic list of Terraform's benefits would.

🛑

The plan that caught a near-miss before it happened

Midway through renaming the schemas to BRONZE/SILVER/GOLD, a routine terraform plan came back showing all three schemas — the ones holding every trade, every rejected message, all the currently-loaded data — marked must be replaced. A single missing setting (is_transient) had drifted between what was actually in Snowflake and what the config said, and Terraform's default behavior for that particular attribute is destroy-then-recreate.

✅ Because plan shows every intended action before anything happens, this was caught and fixed with one line of config — instead of discovering it the hard way, after apply had already dropped three schemas.
🔀

Local and CI disagreeing about what already existed

Early on, the GitHub Actions apply job failed with errors like "a policy called snowflake-fx-rates-read-policy already exists." The workflow checked out a fresh copy of the repository with no memory of what earlier local apply runs had already built, so it tried to create everything again from scratch and collided with itself.

✅ The fix was a shared, remote state backend (S3) instead of a local file. It's the same principle as a shared calendar instead of everyone keeping their own: local runs and CI now check the same source of truth before touching anything, and a locking mechanism stops two runs from writing to it at the same moment (verified live — it correctly blocked a second concurrent run rather than corrupting anything).
🧩

Solving a chicken-and-egg problem in one step

Snowflake's connection to the S3 bucket needs an AWS IAM role that trusts it — but that role's trust policy needs an ID that Snowflake only generates after the connection exists, and the connection needs the role's address as an input. Neither can go first.

✅ Terraform resolved this within a single apply: the role's AWS address is predictable ahead of time (account ID + role name), so the Snowflake side could be created first using that predicted address, and the AWS role's trust policy was then filled in with the values Snowflake generated — all figured out automatically from the dependencies written in the config, not manually sequenced by hand.
💡 The common thread: in all three cases, the value wasn't "Terraform makes infrastructure faster to create" — it was that the plan, the shared state, and the dependency graph each independently prevented a real mistake that manual console clicks would not have caught in the same way.
